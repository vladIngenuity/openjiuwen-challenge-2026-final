# openJiuwen Challenge 2026: harness команды «Индийская техподдержка»

Актуальная техническая документация: [архитектура, справочник функций и
контейнерный запуск](docs/project/README.md). Для ограничения ровно восемью
логическими CPU используйте `tools/run_container.sh` и его `CPUSET`; пример
ниже показывает базовый запуск без привязки CPU.

Harness кодового агента на **openJiuwen 0.1.19**. Он решает максимум задач из 100 за фиксированный бюджет токенов. Главная идея: **токены — самый дорогой ресурс, поэтому всё, что можно посчитать кодом, считается кодом**. LLM подключается только к тому, что детерминированные решатели не разобрали уверенно, и в этих случаях модель пишет код, а не ответ.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --cpus 8 --memory 16g --pids-limit 512 --security-opt no-new-privileges \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

| Параметр | Откуда берётся |
| --- | --- |
| каталог задач | `--tasks-dir`, иначе `$TASKS`, иначе `/data/tasks` |
| файл результатов | `--out`, иначе `$OUT`. Сводка `results.json` перезаписывается атомарно после **каждой** задачи |
| бюджет | `$BUDGET`, по умолчанию 100000 |
| прокси | `$LLM_BASE_URL`, `$LLM_API_KEY`. Ключей в репозитории нет |
| стратегия образа | `empirical_hybrid` через `HARNESS_STRATEGY` в Dockerfile; штатная команда организаторов не передаёт `--strategy` |

Текстовый ответ сохраняется сразу после решения в `answer.txt` рядом с `task.json`. Для пропуска новый файл не создаётся. Запускайте с чистой копией набора, чтобы в ней не было ответов прошлых прогонов. Coding оценивается по исходникам в `workspace/`. Патч проверяется в отдельной копии с оригинальными публичными тестами и публикуется атомарно. Маркер `DONE` сохраняется для заданий, где его явно требует условие.

Каталоги задач на хосте должны разрешать запись процессу внутри контейнера. Флаг монтирования `:rw` сам по себе не даёт права на создание `answer.txt` в каталоге с правами `755`, принадлежащем другому пользователю: это воспроизведено с конкурсным `--cap-drop ALL`. Проверка CI выдаёт тестовой копии права на запись перед запуском.

Сборка проверяет API openJiuwen. После сборки проверьте восемь примеров без сети, под непривилегированным пользователем, с теми же ограничениями, что при запуске:

```bash
docker run --rm --network none --read-only --tmpfs /tmp:rw,size=2g \
  --user 1000:1000 --cap-drop ALL --pids-limit 512 --security-opt no-new-privileges \
  --entrypoint python hack:latest /app/tools/selfcheck.py
```

Для выполнения Python и тестов требуется Linux x86-64 или ARM64 с включённым Landlock ABI 3+ и доступными системными вызовами Landlock в профиле контейнера. Каждый такой процесс получает отдельную копию задачи, ограниченное окружение, отключённые сокеты и лимиты времени, памяти и вывода. Если изоляцию включить нельзя, процесс задачи не запускается. Ограничения Docker по числу процессов и размеру tmpfs действуют на весь контейнер. [Требования ядра к Landlock](https://docs.kernel.org/userspace-api/landlock.html#kernel-support)

Версии зафиксированы: базовый образ `python:3.12.8-slim-bookworm`, `openjiuwen==0.1.19`, все 171 транзитивная зависимость закреплены в `constraints.txt`. Список получен из `uv.lock` самого openJiuwen на теге `v0.1.19`.

## Разработка на Windows (без Docker)

1. `tools\win\setup.cmd` (двойной щелчок): находит или ставит Python 3.12 (openJiuwen не поддерживает 3.14), создаёт `.venv` с закреплёнными зависимостями и проверяет API openJiuwen офлайн.
2. `tools\win\probe.cmd`: проверяет реальный прокси. Скрипт спрашивает `LLM_BASE_URL` и ключ (скрытый ввод, ключ живёт только в памяти процесса). Для всех 4 моделей он проверяет ответ через openJiuwen и через HTTP, `usage` с reasoning-токенами, tool calls и мини-задачу. Отчёт записывается в `runs\probe_*.json`; секретов в нём нет, а папка `runs/` в git не попадает. В конце печатается раздел SUMMARY: какие модели отвечают, через какой транспорт, приходят ли reasoning-токены, не превышает ли вывод `max_tokens` и насколько наша оценка входа расходится с фактической. Расход: около 2–5 тыс. токенов, жёсткий потолок 8000.
3. `tools\win\docker_check.cmd` (Docker Desktop в режиме Linux) проверяет восемь примеров без сети. Через Docker можно также запустить необязательный прогон с прокси. Результаты в `runs\docker_*\`.

## Архитектура

```
scan (100 задач, поле expected выбрасывается при чтении)
  │
  ├─ Фаза A — детерминированные решатели (0 токенов, ~5 с на 100 задач)
  │    math    : грамматика операций «всё или ничего»: не понято хоть одно
  │              предложение → задача уходит дальше, без догадок
  │    search  : markdown-KB → граф сущностей; цепочки отношений из вопроса,
  │              словарь отношений строится по ключам самой базы + синонимы
  │    data    : строгие шаблоны вопросов (сумма/выручка/число заказов с
  │              фильтрами); весь хвост вопроса должен быть «съеден» фильтрами
  │    coding  : автоматический ремонт программ инверсией мутаций (см. ниже)
  │
  ├─ Фаза B — одиночный дешёвый вызов LLM, порядок по reward·p/cost
  │    math/data: модель пишет Python-программу, мы исполняем её в песочнице
  │    search   : в промпт попадает только релевантный срез KB (1–2 хопа)
  │    coding   : полный исправленный файл + вывод тестов, проверка тестами
  │
  ├─ Фаза C — эскалация: вторая модель, затем агент с инструментами
  │    (openJiuwen @tool/LocalFunction: list/read/write_file, run_python,
  │     run_shell, submit), жёсткий лимит токенов на задачу, старые выводы
  │     инструментов в истории обрезаются
  │
  └─ Фаза D — перекрёстная проверка LLM-ответов (если бюджет > 35%):
       вторая модель; при расхождении — модель с рассуждениями; большинство голосов
```

LLM вызывается через `openjiuwen.core.foundation.llm.Model` (OpenAI-совместимый клиент). Если сам фреймворк падает с ошибкой, не связанной с прокси, вызов повторяется через минимальный HTTP-транспорт. Так несовместимость версии не обнулит прогон. Оба пути идут через один учёт бюджета.

### Coding: ремонт без LLM

Тестовые задачи в coding получаются внесением мелких мутаций. Поэтому harness:

1. Запускает тесты в копии workspace и по выводу находит упавшие тесты.
2. По AST тестов определяет, какие функции они вызывают, включая транзитивные вызовы внутри модуля.
3. Перебирает однократные правки этих функций: сравнения, арифметические операторы, константы ±1, срезы, взаимозаменяемые builtin-функции и методы (`sorted`↔`reversed`, `min`↔`max`, `upper`/`lower`/`capitalize`…), `and`↔`or`, отрицание условия, удаление оператора, подмену имён.
4. Прогоняет всех мутантов в отдельном процессе с таймаутами и лимитом памяти.
5. **Учитывает, что оценка идёт скрытыми тестами.** Если видимые тесты проходят несколько мутантов, они сравниваются на случайных входах, построенных по примерам из тестов. Затем выбирается поведенческий кластер: по совпадению с эталонной семантикой для частых имён функций, а при отсутствии эталона — по взвешенному голосу. Штрафуются кластеры, эквивалентные удалению строки, и вырожденные кластеры с константным выходом.

На сгенерированных наборах (Task Factory) исправления прошли **100% скрытых тестов**: 0 ошибок более чем на 300 coding-задачах.

## Формат результата (согласован с командой)

На каждую задачу в `results.json` (`--out` / `$OUT`) и в траектории (`$HARNESS_TRACE`) пишется запись:
`task_id, type, reward, status, answer, verify, solver, calls[], cost_total, seconds, note`.

* `status`:
  * `verified` — ответ проверен тестами задачи (coding);
  * `answered_unverified` — ответ записан, но его правильность неизвестна до проверки организаторами;
  * `infeasible_claimed` — harness считает задачу невыполнимой (это утверждение, а не факт);
  * `skipped` — пропущена из-за бюджета или времени;
  * `failed` — решить не удалось.
* `verify`: `unittest | det_parse | vote | none`. Голосование и кластеризация поведения — эвристики, а не независимая проверка.
* `calls[]`: модель, транспорт (`openjiuwen` / `raw`), токены входа, выхода и рассуждений, стоимость, время, ошибка.
* Онлайн-оценка вероятности успеха обновляется **только по проверенным исходам** (coding → тесты). Для остальных типов во время прогона правильность неизвестна, поэтому используются априорные значения.

**Пустая выборка в data** (продукта нет в таблице, месяцы вне данных). Семантика не подтверждена организаторами. По умолчанию (`HARNESS_EMPTY_SELECTION=zero`) ответ 0 с пометкой `DISPUTED` в `note`: SUM или COUNT по пустой выборке полной таблицы равны 0. Режим `infeasible` вместо этого считает такую задачу невыполнимой. В генераторе есть независимые выполнимые случаи с правильным ответом 0.

### Data Solver: спорные случаи (покрыты `tests/test_data_solver.py`)

| Случай | Поведение |
| --- | --- |
| значения фильтра с пробелами или в другом регистре (`" Widget "`, `WIDGET`) | нормализуются, учитываются |
| пустое числовое значение в нужной строке | ответ не угадывается, задача уходит в LLM |
| дубликаты строк | считаются как отдельные заказы, без дедупликации |
| продукт есть, но нет продаж в диапазоне месяцев внутри данных | **выполнимо**, ответ 0 при любой политике |
| продукта нет в таблице или диапазон вне данных | `DISPUTED`: 0 (`zero`) или `infeasible` (`HARNESS_EMPTY_SELECTION`) |
| инвертированный диапазон («months 3 through 1») | задача уходит в LLM, формулировку решает модель |
| в CSV нет объявленного в условии столбца | `maybe_infeasible` (сигнал, не утверждение): задача уходит в LLM с пониженным приоритетом |
| нет файла CSV | `infeasible_claimed` |
| перестановка строк или столбцов | ответ не меняется (метаморфные тесты) |

## Стратегии (контракт Strategy/Executor)

Решения о бюджете (порядок задач, лимиты, модели, эскалация, перепроверка, диагностика) принимает стратегия. Контракт описан в `docs/contracts/strategy.md`, код — в `harness/strategy.py`. Исполнитель (`harness/executor.py`) работает с ней так:

* до 5 параллельных воркеров;
* перед каждой попыткой вызывает `order()` заново;
* каждая попытка записывается как отдельный `AttemptResult`;
* каждая попытка, голосование и диагностика выполняются в своей области лимита (`llm.cap_scope`): `max_tokens` каждого вызова урезается до остатка, общий реестр бюджета проверяется всегда;
* `budget_for() < MIN_CAP` или отказ реестра до первого вызова откладывают задачу до завершения следующей попытки (без траты токенов); всё, что осталось `pending` к концу, становится `skipped`, а не `failed`.

* `python run_agent.py --tasks-dir T --strategy baseline` — базовая стратегия при локальном запуске Python без переменной `HARNESS_STRATEGY`. Это прежняя логика, выраженная через контракт. С нулевым шумом mock она даёт **те же** баллы, расход и число вызовов, что `legacy`.
* `--strategy legacy` — старый код фаз B–D, оставлен для сравнения.
* Новая стратегия: файл в `harness/strategies/`, запись в `STRATEGIES` и проверка `check_strategy()`.
* `python tools/compare.py --strategies baseline,lean --seeds 1,2,3 --mode mock` прогоняет все стратегии на одних и тех же задачах Task Factory с одинаковым бюджетом. Отчёт пишется в `docs/research/<mock|real>/compare_*.md`. Режим `--mode real` тратит реальные токены.

## Лимиты бесплатной фазы и изоляция (issue #15)

* `HARNESS_DET_TASK_SECONDS` (30) — предел на детерминированный ремонт одной coding-задачи; `HARNESS_DET_PHASE_SECONDS` (90) — предел на всю фазу без токенов (и не больше четверти оставшегося времени). Задача, не уложившаяся в лимит, не угадывается, а уходит модели. На партии batch-022 (100 разнородных задач, без LLM): было 146 с и 7 внутренне проверенных coding-задач, стало 58 с и 6.
* Исправление, которое лишь удаляет оператор, считается слабым: если модель доступна, сначала пробует она, а слабое исправление применяется в конце как запасной вариант.
* `HARNESS_ISOLATION=auto|strict|off` (по умолчанию `strict`): без Landlock/seccomp исполнение запрещено. `auto` — явный режим для доверенных входов: отдельная проверка изоляции до исполнения кода, затем при её недоступности только лимиты ресурсов. Вывод задачи не может отключить защиту. `off` оставляет только лимиты ресурсов; приватное оценивание требует `strict`.
* Прямой HTTP-транспорт работает и без `httpx` (stdlib) и различает коды ошибок провайдера: `insufficient_quota` — квота, `model_not_found` — смена модели.

## Порядок для coding и режим изоляции в образе (12.11)

* Приватная проверка на авторских задачах (PR #20): из 6 детерминированных ремонтов, прошедших видимые тесты, скрытые тесты прошёл 1. Поэтому при доступной модели coding-задачу сначала решает модель, а бесплатный ремонт применяется только как запасной вариант (если модель не дала проверенного решения или кончился бюджет). `HARNESS_DET_CODING=first` возвращает прежний порядок.
* В образе задано `HARNESS_ISOLATION=auto`: доверенная предпроверка включает Landlock + seccomp, а если ядро их не даёт — код исполняется с лимитами ресурсов и это пишется в лог. Значение по умолчанию в коде — `strict`.

## Потолок расхода на одну задачу (12.11)

`HARNESS_TASK_CAP` (1500) — консервативный потолок обычных попыток одной задачи; `HARNESS_AGENT_CAP` (1200) — потолок одной эскалированной попытки; голосование ограничено 600. В `empirical_hybrid` после первого прохода только ответы, явно обрезанные провайдером с известным `usage`, получают одну дополнительную попытку: до 2400 единиц за попытку и до 4000 за задачу вместе. Эта попытка использует модель без reasoning и не расходует последние 5000 единиц стратегического резерва. Неопределённый ответ API останавливает реестр и никогда не повторяется.

## Учёт бюджета

* Стоимость равна `output + 0.1·input`. По умолчанию `completion_tokens` уже включает reasoning. Установите `HARNESS_REASONING_USAGE=separate`, если прокси подтверждает, что reasoning возвращается сверх `completion_tokens`. Кеш провайдера не учитывается.
* У каждой физической отправки есть резерв и запись с `request_id`. Резерв равен `0.1·оценка_входа + max_tokens`. Он должен помещаться в остаток общего бюджета и лимит попытки.
* Успех списывается по `usage`. Ошибка после отправки, таймаут, обрыв и отмена списывают полный резерв и останавливают новые вызовы. При отсутствии надёжного `usage` или превышении лимита вывода новые вызовы также останавливаются. Поле `accounting` отличает измеренный расход от неопределённого.
* Автоматических повторов после ошибки транспорта или неизвестного списания нет. Дополнительная попытка после `finish_reason=length` разрешена только при полученном и учтённом `usage` и доступном бюджете.
* По умолчанию используется `qwen3.8-27b-noreason`. Цена в конкурсе зависит только от числа токенов, а не от модели. Поэтому берём самую сильную модель без рассуждений, а рассуждающая включается только для голосования и её `max_tokens` ограничен.
* Стоимость и вероятность успеха задачи оцениваются по типу (априорные значения плюс онлайн-обновление по ходу прогона), для coding — по размеру файлов.

## Невыполнимые задачи

Мы различаем три ситуации: «данных нет», «наш парсер не понял» и «трудно».

* **Детерминированно, бесплатно.** В KB нет упомянутой сущности. В CSV нет значения фильтра (например, продукта) или диапазон месяцев вне данных. Нет файла с данными. В coding невыполнимость видна по тому, что ни одна правка не проходит противоречивые тесты.
* **Цепочка в KB рвётся на отсутствующем атрибуте.** Это только сигнал `maybe_infeasible`. Задача уходит на дешёвую LLM-проверку с пониженным приоритетом и помечается невыполнимой, только если модель с этим согласна.
* **LLM-путь.** Модель может явно ответить `INFEASIBLE`. Невыполнимой задача считается, только если это подтвердили две разные модели.
* Если парсер просто не понял задачу, она **никогда** не считается невыполнимой: такие задачи передаются в LLM.

## Траектории и проверка

| Инструмент | Что делает |
| --- | --- |
| `tools/task_factory.py` | генератор задач всех 4 типов. В задачах есть формулировки вне грамматики решателей, управляемая доля невыполнимых, а для coding — скрытые тесты. Эталон лежит вне каталога задач |
| `tools/evaluate.py` | счёт по скрытым тестам и эталону, учёт невыполнимых задач |
| `tools/mock_llm.py` | OpenAI-совместимый mock прокси: отвечает по эталону с шумом, отдаёт `usage`, поддерживает tool calls, выдаёт 5% ошибок HTTP 500 и 402 после исчерпания бюджета |
| `tools/probe_proxy.py` | проверка реального прокси: все 4 модели через openJiuwen и через HTTP, печатает фактический `usage` |
| `/tmp/harness_trace.json` | траектория прогона: каждый вызов (модель, вход, выход, reasoning, стоимость) и итог по задачам |

Результаты на 5 независимых наборах по 100 задач (около 20% невыполнимых):

| Режим | Доля достижимых баллов | Неверных ответов | Токенов |
| --- | --- | --- | --- |
| без LLM (только детерминированные решатели) | 83,9% | 0 | 0 |
| mock LLM с 15% неверных ответов | 98,9% | 3 (все из-за шума mock) | ~3,7 тыс. из 100 тыс. |

Важно: эти цифры получены на нашем генераторе, а не на настоящих Qwen. Реальные траектории собираются тем же `/tmp/harness_trace.json` после прогона с ключом прокси.
