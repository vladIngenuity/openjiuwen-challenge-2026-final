# Контракт Strategy / Executor (v1.0)

Согласован в Telegram 9 ноября 2026 между Claude (агент Артёма) и агентом Влада. Код: `harness/strategy.py`. Изменения контракта вносятся только через PR с ревью обеих сторон.

## Разделение ответственности

| Strategy (Влад) | Executor (Артём) |
| --- | --- |
| решает, какую задачу брать, с каким лимитом и какой моделью | выполняет попытки, вызывает Qwen через openJiuwen |
| решает, эскалировать ли, перепроверять ли, диагностировать ли | ведёт общий бюджет, ничего не тратит сверх него |
| чистая логика: без LLM-вызовов, без файлов, без побочных эффектов | пишет `answer.txt`, `results.json`, журнал вызовов |

## Цикл исполнения

1. Executor сканирует задачи и бесплатно (0 токенов, но не 0 времени) прогоняет детерминированные решатели. Результат попадает в `TaskView.det_status`.
2. Пока есть бюджет, время и задачи в статусе `pending`, каждый из воркеров повторяет:
   1. Пересобирает `RunState` и вызывает `order(pending_tasks, state)`. **Это происходит перед каждым выбором задачи, то есть после каждой завершённой попытки.**
   2. Берёт первую задачу из очереди, которой нет в `state.deferred` и `state.in_flight`.
   3. Если `should_diagnose(task, state)`, вызывает LLM-диагностику (лимит `DIAG_CAP`, см. ниже). Её расход идёт с тегом `plan:<task_id>`, результат кладётся в `state.diagnostics[task_id]`.
   4. Запрашивает лимит `budget_for(task, state)` и обрезает его до `state.remaining`. Если лимит меньше `MIN_CAP`, задача **откладывается** (см. переходы).
   5. Делает попытку моделью `model_for(task, state, attempt)` в рамках лимита и получает `AttemptResult`.
   6. Если ответ не проверен и `should_verify(...)`, получает второе мнение (`kind=vote`, лимит `vote_cap`). Задача на этом закрывается.
   7. Если попытка не дала ответа и `should_escalate(...)`, задача **остаётся `pending`**, а следующую попытку (`attempt+1`, вплоть до агента с инструментами) назначит `order()` на следующих итерациях. Иначе задача закрывается.
3. Executor останавливается при `proxy_dead`, исчерпании бюджета или времени. Все оставшиеся `pending` задачи становятся `skipped`.

## Переходы состояний задачи

```
pending ──попытка──▶ verified | answered_unverified            (ответ записан, конец)
pending ──попытка──▶ pending        если не удалось и should_escalate = true
pending ──попытка──▶ infeasible_claimed | failed                если should_escalate = false
pending ──отложить──▶ pending (в state.deferred)                 budget_for < MIN_CAP
                                                                или реестр отказал в резерве
pending ──конец прогона──▶ skipped
```

* `order()` получает **все** `pending` задачи, включая отложенные (`state.deferred`) и уже выполняемые (`state.in_flight`), чтобы стратегия видела полную картину. Executor их пропускает при выборе.
* **Отложенная задача** не тратит токенов и не считается попыткой. Она возвращается в выбор, как только завершится любая другая попытка (состояние изменилось, `budget_for` может ответить иначе). Если все оставшиеся задачи отложены и ничего не выполняется, прогон заканчивается, а они становятся `skipped`.
* **Явно отложить задачу** стратегия может двумя способами: не включать её в `order()` или вернуть `budget_for < MIN_CAP`. Первый способ подходит, чтобы держать задачу в резерве; второй — чтобы сказать «сейчас не хватает средств».
* Номер попытки = число завершённых попыток задачи (без `vote`) + 1. Отложенные попытки и отказы реестра номер не увеличивают.
* Финальные статусы (`verified`, `answered_unverified`, `infeasible_claimed`, `failed`, `skipped`) больше не меняются. Исключение — `vote`, который может заменить ответ в `answered_unverified` при большинстве 2 из 3.

## Ограничение расходов

Каждый LLM-вызов проходит через общий реестр бюджета и **несколько уровней лимитов**:

| уровень | кто задаёт | значение | как обеспечивается |
| --- | --- | --- | --- |
| весь прогон | реестр | `budget_total − резерв безопасности` | перед каждым вызовом резервируется `0.1·input_est + max_tokens`; если не хватает, вызов не делается (`LLMUnavailable("budget")`) |
| попытка | `budget_for()` | от `MIN_CAP` до `state.remaining` | все вызовы попытки идут в одной области лимита: `max_tokens` каждого вызова урезается до остатка области; если остаток < 30, вызов не делается |
| диагностика | контракт | `DIAG_CAP = 150` | своя область лимита; не запускается, если `state.remaining < DIAG_CAP` |
| голосование | `Strategy.vote_cap` (по умолчанию `VOTE_CAP_DEFAULT = 1200`) | до 2 доп. вызовов | своя область лимита; не запускается, если `state.remaining < vote_cap` |

* Лимит области проверяется **на резервировании**, поэтому вывод модели жёстко ограничен. Превышение возможно только на ошибке оценки входа (вес 0.1), на практике единицы процентов.
* Executor **всегда** сверяется с общим остатком: никакой лимит стратегии не может разрешить вызов, который реестр не может зарезервировать.
* Сеть: Явные отказы 4xx списываются по оценке входа. Таймаут, обрыв и отмена после отправки списывают полный резерв. Каждый повтор резервируется и журналируется отдельно.
* Отказ по бюджету или лимиту до первого вызова попытки = отложить задачу (без попытки). Отказ посреди попытки = попытка завершилась неудачей, потраченное учтено.

## Единицы и учёт

* `budget_for`, `cost`, `spent`, `remaining`, `est_cost` измеряются в **конкурсных единицах**: `output + 0.1·input`. Reasoning-токены входят в output.
* Реальные `input_tokens`, `output_tokens` и `reasoning_tokens` пишутся отдельно в `Call`.
* Расход на планирование (диагностику) отделяется по тегу `plan:`, чтобы честно сравнивать Lean и Deliberative.

## Семантика статусов (это гипотезы, не истина)

| status | значение |
| --- | --- |
| `verified` | ответ прошёл **нашу** проверку (для coding — тесты задачи). Скрытые тесты организаторов могут не пройти |
| `answered_unverified` | ответ записан, его правильность неизвестна |
| `infeasible_claimed` | harness считает задачу невыполнимой. Это утверждение, а не факт |
| `skipped` | не пытались: не хватило бюджета или времени, или стратегия вернула 0 |
| `failed` | пытались, ответа нет |

`verify ∈ {unittest, det_parse, vote, none}` описывает способ проверки, но не гарантирует правильность.

## Требования к реализации Strategy

* Методы быстрые (< 10 мс), детерминированные при одинаковом входе, без побочных эффектов.
* `order` возвращает только id из переданного списка `tasks` (все они `pending`).
* Необязательный атрибут `vote_cap: float` задаёт лимит голосования; иначе `VOTE_CAP_DEFAULT`.
* `model_for` учитывает `state.unavailable_models`: модели с ответом 403/404 Executor отключает.
* Проверка соответствия контракту: `harness.strategy.check_strategy(obj)` должна вернуть пустой список.
